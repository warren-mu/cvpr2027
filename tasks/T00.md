# T00 可行性测试（Hopper，单张 H200）

**目标**：测清楚在 Hopper 上能不能跑我们的实验，以及要多少算力。全程只用 1 张 H200，总共不超过 6 GPU·小时。
**可以并行**：否。
**最关键的问题**：H200 的图形硬件很少，AI2-THOR 渲染就算能跑，也可能慢到拖垮强化学习的采样。所以第 2 步的渲染吞吐量是本任务最重要的数字。

## 要做

### 0. 登录节点上的准备（只做轻量操作）
- 查清楚并写进报告：
  - home 和 scratch 的配额，以及定期清理规则；
  - `module avail` 里有哪些 cuda 和 conda；
  - 登录节点能否访问 pypi、github、huggingface；
  - `hpc autox` 给出的示例提交命令。
- 照着 `hpc autox` 的示例，写一个 1 张 GPU 的作业模板 `scripts/pbs/job_1gpu.pbs`：项目 `CFP04-SF-125`、Express 队列、1 张 GPU、12 核，walltime 由参数传入。作业里要先 `cd` 到仓库目录，并通过 `scripts/run_logged.py` 运行传进来的命令。

### 1. 环境（不需要 GPU）
- 写 `scripts/setup_env.sh` 并运行。如果登录节点不允许跑这么重的任务，就申请一个只要 CPU 的作业来跑。
  - Miniforge 装在配额够大的目录；
  - `git clone https://github.com/mll-lab-nu/VAGEN third_party/VAGEN`，在脚本里固定 commit；
  - 严格按 VAGEN README 建 conda 环境 `cvpr2027`，版本以 README 为准；
  - pip、conda、HF、torch、triton、ray 的缓存和 `TMPDIR` 放到 scratch；把 `~/.ai2thor` 软链到 scratch。
- 集群上没有 sudo。缺 Vulkan 相关的库时，先查系统里有没有、`module` 里有没有，再考虑 conda-forge。都没有就如实报告，不要绕过集群规定。
- 如果计算节点不能上网，要在登录节点上提前下载好 AI2-THOR 的程序文件和 `Qwen/Qwen2.5-VL-3B-Instruct` 的权重，放到 scratch。

### 2. GPU 作业 A：渲染（不超过 1.5 小时）
先跑下面几条，输出存进 `logs/`（失败也保存错误输出）：
```bash
nvidia-smi > logs/nvidia_smi.txt
vulkaninfo --summary > logs/vulkaninfo.txt 2>&1
pip freeze > logs/env_freeze.txt
```
再确认计算节点能不能上网，然后跑两个检查。

**`src/envs/thor_checks.py`**：用 run_logged 运行，名字 `t00_thor_checks`。用 CloudRendering 启动一个场景（例如 FloorPlan1），然后：
- **渲染**：渲染一帧，存到 `logs/thor_smoke.png`（分辨率不低于 224×224）。
- **确定性恢复**：随机生成 20 个状态。对每个状态，记录**完整的**物体位姿列表（`SetObjectPoses` 会删掉列表里没有的可移动物体，见 METRICS_SPEC §1），用它恢复两次，比较两帧。报告逐像素最大差值的最大值（期望为 0），以及失败的状态数。
- **实例分割**：打开 `renderInstanceSegmentation`，报告第一帧里的实例数，以及掩码能对上 metadata 物体 id 的比例。
- **挪动单个物体**：挑 10 个可拾取物体，各挪动一次。报告目标位置与实际位置的误差（中位数、最大值），以及有多少其他物体被意外移动超过 1cm。

**`src/envs/thor_throughput.py`**：用 run_logged 运行，名字 `t00_thor_throughput`。分辨率测两档：224×224，以及 VAGEN Navigation 的默认分辨率。
- 单个 AI2-THOR 实例连续做 200 次"移动＋渲染"，报告每秒帧数（取中位数）。
- 同时开 K = 1、4、8、11 个实例，报告总帧数每秒、每个实例平均占多少 CPU、显存占多少。
- 这是 H200 上的数字。报告里写明：它和 VAGEN 冒烟训练每步需要的帧数相比，够不够用。

两个脚本都把指标写入对应的 results JSON，并打印 `FINAL_METRICS_JSON`。

### 3. GPU 作业 B：VAGEN Navigation 短冒烟训练（不超过 2 小时）
写 `experiments/t00_vagen_smoke.sh`：先跑训练，再用 `src/tools/parse_train_log.py` 从训练日志里提取数字，写入 `results/t00_vagen_smoke.json` 并打印 `FINAL_METRICS_JSON`。整个脚本用 run_logged 运行，名字 `t00_vagen_smoke`。
- 用 VAGEN 官方的 Navigation 配置，只允许两处改动：GPU 数改成 1；总步数缩短到 60 分钟内能跑完。
- 显存不够就如实记录。然后可以尝试官方支持的省显存选项，每种尝试单独用 run_logged 跑一次，名字加后缀。
- 需要的数字：
  - 每个训练 step 的耗时（中位数），以及其中 rollout（含渲染）和参数更新各占多少；
  - 显存峰值、CPU 和内存占用；
  - 官方完整配置的总 step 数；
  - 据此估算的单卡完整训练小时数，写明公式。

### 4. 报告
写 `tasks/T00.report.md`，提交并推送，然后停下。报告里除了上面要求的内容，还要写：
- 每个 PBS 作业的作业号、walltime、实际用掉的 GPU·小时，以及合计；
- 一张卡上能同时跑几次训练（受 12 个 CPU 核和渲染吞吐量限制），给出依据。

## 验收标准（Claude 审查时会逐条检查）
- `python3 scripts/audit_provenance.py` 没有 FAIL。
- `logs/thor_smoke.png` 是真实渲染出来的画面（Claude 会直接看这张图）。
- 确定性恢复失败数为 0；不为 0 时，报告里写明原因和失败样例。
- 渲染吞吐量的每个数字都能在 `logs/runs/t00_thor_throughput.log` 里找到。
- 冒烟训练 exit_code 为 0，并且跑了至少 20 个 step；没做到就如实报告失败原因。
- 算力估算用到的每个输入数字都能在日志里找到出处。
- `setup_env.sh` 能在新账号上从零重建环境（Claude 会通读脚本，检查有没有遗漏的步骤）。
- GPU·小时合计不超过 6；超过的话，报告里要写明原因。
