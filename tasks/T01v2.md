# T01 v2 按构造生成世界对（取代 T01 v1 的随机采样加拒绝）

**为什么改**：v1 共 31 次尝试，0 对通过。主要的拒绝原因是「目标不唯一或关系无法解析」，以及「找不到合格的前缀和一步证据视角」。v2 改为**先定好要的结构，再按结构构造**，并用物理引擎的落定反应判定物理有效性（见 `reviews/T01_collision.md`）。
**GPU 预算**：试点集不超过 8 GPU·小时；作业打包方式沿用已验证的多卡 manifest。
**目标时间**：周一（11/9）美东上午前交出试点集。

## 任务结构：「离锚点最近的那个」
- 指令模板：`Select the <类别> closest to the <锚点类别>.`
- 候选：同一类别的两个可拾取物体 A、B。在起点视点 v0 的画面里，两者都可见，各自的掩码 ≥ 250 像素，并且都带标号。场景里同类物体不足两个时，可以用 `SetObjectPoses` 在完整列表里重复列出同一个物体来复制一份，放到合法放置点。
- 锚点 X：另一个类别的可拾取物体。
  - w0：X 放在 A 附近，满足 dist(X, B) ≥ 1.5 × dist(X, A)，按这个间隔保证目标唯一；
  - w1 唯一的编辑是**只挪动 X**：
    - Flip：X 挪到 B 附近，满足镜像的间隔条件；
    - Stay：X 挪到 A 附近的另一个位置，仍满足间隔条件。
- 四种情况：
  - **Look 类**：X 在 v0 的前缀画面里不可见（两个世界中 X 的掩码都是 0）。执行**一个观察动作**（左转或右转 45°，或者移动到相邻视点）之后，X 在两个世界都可见（掩码 ≥ 250 像素），且证据像素满足 METRICS_SPEC §1。
  - **直接类**：X 在 v0 的画面里就可见，并在 t=0 满足证据像素标准。
- 这个结构下，过早承诺就是不看 X 直接选 A 或 B，正好是论文要研究的「蒙」。

## 构造步骤（每个场景）
1. **场景落定预检**：原始场景推进物理，直到静止。超过 N 步仍未静止，或有物体位移 > 1 cm，就排除整个场景并记录原因。
2. 在导航图上选 v0 和朝向，满足 A、B 同时可见。用接收面采样，枚举 X 的候选放置点，按上面的间隔和可见性条件筛选。
3. **同一个进程、agent 不动**：构造 w0 → 落定 → 检查物理有效 → 保存快照 → 渲染前缀。用 `SetObjectPoses` 切到 w1 → 落定 → 检查物理有效 → 保存快照 → 渲染前缀。比较前缀（METRICS_SPEC §1 的信息一致）。
4. 观察动作之后的画面，同样在两个世界各渲染一次，计算证据像素。
5. **见证**：在导航图上用知道真实状态的规划器求最短动作序列。Look 类的见证一般是「观察 → 必要时转回 → select」。然后在一个新进程里，从快照恢复后回放；两个世界都要成功。
6. 四种情况数量均衡，Look→Flip 与 Look→Stay 之比在 0.8–1.25。

## 产出与验收

  3. 两个世界中正确目标的框。

- 验收：审计无 FAIL；Claude 抽看 40 张审查图通过；见证回放在两个世界都成功。

## 补充（2026-11-08 14:00，根据厨房首轮 0 对的结果；这是 Claude 的规格写得不清楚，不是实现错误）
1. **场景落定预检的基准改为「落定后的状态」，不再是场景原始摆放。** 原始 iTHOR 场景里，不少物体在恢复物理后会下沉几毫米到几厘米，这本身不说明场景有问题。新的预检做法：
   - 先推进物理，直到落定。落定的判据：原生 `isSceneAtRest=true`，或者连续 10 步每个物体的单步位移都 < 1 mm，两者满足其一即可。超过 N 步仍未落定，就排除场景。
   - 落定过程中，有物体位移超过 0.5 m（说明穿过地面或掉出场景），也排除场景。
   - 落定后再推进 M 步作为稳定窗口（M 写进配置，建议 50 步）。窗口内任何物体相对落定状态移动 > 1 cm，就排除场景。
   - **落定后的快照就是这个场景的基准世界。** 之后「其他物体位移 ≤ 1 cm」「编辑物体偏差 ≤ 2 cm」都相对这个基准衡量。
2. **锚点 X 的放置**：优先用原生的点放置动作（如 `PlaceObjectAtPoint`，如果 AI2-THOR 5.0 支持），让物体底面落在采样点上。「指定位姿」指放置动作完成后的位姿，之后的落定漂移不超过 2 cm 即合格。不要把接收面采样点直接当作物体中心写入。
3. **证据存储**：被拒绝的尝试只保存一条简短 JSON（拒绝原因、关键数值）和一张小缩略图；完整原始证据只为合格的世界对，以及每种拒绝原因各前 3 个样例保存。避免再次触碰存储上限。
4. 厨房的 12 个场景按新预检重跑，与第二轮复制候选合并成一个作业；客厅首轮如果还没开始，取消后按新预检重提。合计仍在 T01v2 的 8 GPU·小时子预算内。
5. 报告里给出每个场景的预检结果，以及物理检查拒绝原因的分布：编辑物体偏差、其他物体位移、接收面归属，各有多少。

## 补充 2（2026-11-08 14:10，Claude 复查规格时发现的两处问题，提交下一轮作业前必须改）
1. **Look 类的证据条件写得比 METRICS_SPEC 还严，要放宽到与 METRICS_SPEC 一致。** 原文要求「观察后 X 在两个世界都可见」。但在 Look→Flip 里，X 在 w0 位于 A 附近，在 w1 位于 B 附近，同一个观察动作通常只能看到其中一处。其实「在 A 附近没看到 X」本身就是证据，智能体可以继续去看 B 附近。所以改为：
   - **Look 类**：v0 前缀中两个世界的 X 掩码都为 0（不变）；第一个观察动作之后，两个世界的帧在 X 掩码并集内的证据像素 ≥ 250（即 METRICS_SPEC §1 的定义，不放宽）。智能体之后可能还需要更多观察，这由两个世界各自的见证动作保证可完成（见证上限 12 步不变）。
   - **直接类**：X 在两个世界的 v0 画面里**都**可见（各自掩码 ≥ 250），并且 t=0 时证据像素达标。这样才满足「t 时刻证据已足够」。
2. **起点 v0 必须让 A、B 都能立即被选中。** METRICS_SPEC §2 规定，SR 要求 `select` 时所在视点到目标的距离 ≤ 1.5 m。所以 v0 到 A、B 的距离都必须 ≤ 1.5 m，且两者都可见、带标号；否则「不看就直接选」（过早承诺）在 v0 根本做不到，实验设计就失效了。
3. **运行中尽早发现问题**：每个采集作业运行时，每 10 分钟把各类拒绝原因的计数写进 STATUS.md 并推送。前两个场景跑完如果合格数为 0，立刻通知人类和 Claude，不必等作业结束。
4. **提交前先推代码**：每次提交新的采集作业时，先把对应代码推到 GitHub，再提交作业。Claude 会趁排队时审代码；如果发现问题，取消排队中的作业、修改后重提，不额外增加等待时间。

**第二轮代码（626fcf7）里的三处搜索设计，会让同样的问题重演：**
- `identity_sets` 按类别名的字母序枚举锚点，Apple 排在最前，并且一个组合要用完全部放置点才换下一个；
- `clone_source` 选字母序第一个单例物体作为复制源，同样很可能是 Apple；
- 每个场景只尝试一次复制，失败就放弃整个场景；复制成功后，又只保留复制出来的那一组候选，丢掉场景里天然的候选组。

**改法**（都是搜索顺序和类别选择，METRICS_SPEC 的任何阈值都不变）：
1. **锚点 X 只用不会滚动的类别。** 排除球形物体和躺放时会滚的圆柱形物体：Apple、Tomato、Potato、Egg、Lettuce、BasketBall、BaseballBat、Pen、Pencil，以及所有切片、打碎后的变体。名单写进配置。复制源同样排除这些类别；场景里原本就有、不需要移动的候选不受限制。
2. **复制要多试几次。** 按固定顺序遍历合格的复制源（不滚动的单例可拾取物体）。每次尝试照旧用一个新的 Controller，每个场景最多 6 次，第一次成功就停。
3. **天然候选组和复制候选组都保留。** 场景的候选组 = 天然候选组 ∪ 复制成功后的候选组。不要因为启用了复制，就丢掉天然候选组。
4. **搜索要轮换。** 在各个（候选组, 锚点）组合之间轮流尝试，不要把一个组合的放置点用完才换下一个。同一个组合连续 10 次物理检查被拒，就跳过这个组合。
5. **存储上限不能让 worker 失败。** 达到上限后只停止保存原始证据；搜索继续，简短 JSON 照常写。
6. **报告**：按锚点类别给出 w0 物理检查的通过数和尝试数；给出每个场景复制尝试的次数和结果。

## 补充 4（2026-11-08 下午，Claude 复查规格时发现的问题；第二轮 GPU 作业提交前接入）
**问题**：补充 2 把 Look 类的证据条件放宽成「第一个观察动作之后，两个世界在 X 掩码并集内的证据像素 ≥ 250」。这就允许出现下面的 Look→Stay 对：w0 里 X 在 A 旁边、这一步看得见；w1 里 X 也在 A 旁边，但这一步看不见。智能体在 w1 看到「A 旁边没有 X」，会合理地推断 X 在 B 旁边、去选 B，可正确答案是 A。这样的样本没法靠观察做对，会教坏策略。这是 Claude 放宽规则时没想到的。

**新增要求「可解性」**（只对 Look 类；直接类已经要求 X 在两个世界的 v0 都可见，不变）：
1. 在**每个**世界里，至少有一个一步观察动作执行之后，该世界中 X 的掩码 ≥ 250 像素。一步观察动作的集合，就是代码里 `observation_actions` 给出的集合：左转、右转、移到相邻视点。两个世界里可以是不同的动作。
2. 实现：`choose_look` 对全部一步观察动作都要评估，不再提前 `break`。记录每个动作执行后两个世界的 X 像素数，字段 `anchor_visible_actions_w0`、`anchor_visible_actions_w1`，两者都非空才合格。
3. 补充 2 的证据条件不变：共同的第一个观察动作之后，并集内证据像素 ≥ 250。
4. 不满足时的拒绝原因记为 `look_not_solvable_w0` 或 `look_not_solvable_w1`，计入拒绝原因分布。
5. 审查图：Look 类每张加一栏，放每个世界中「能看见 X 的那个视角」的画面。

  - 3 个（FloorPlan3、4、212）报「Common baseline state restoration failed before native proposal queries」，其中两个已经复制成功。
- **最主要的失败原因：`PlaceObjectAtPoint` 报「Spawn area not clear」。** 复制和放置锚点，都是只试一个点、失败就算这次尝试失败；复制失败还要换新 Controller。几乎每个场景都有几十次这类失败。

   - 每次放置最多试 40 个点。这些失败的点不计入尝试次数，但要按场景记录次数。
2. **专门为 Look 类准备一组放置点（投影预筛）。** 对每个起点视角 v0 和每一侧（A 侧、B 侧），把每个原生放置点（加上锚点半高）投影到相机里（AI2-THOR 的实际视场角、agent 位姿、俯仰角、图像尺寸）：
   - 落在 v0 画面内的点 → 直接类候选池，沿用现有的近到远排序；
   - 落在 v0 画面外（离画面边缘至少 10 个像素），但执行某个一步观察动作后落在画面内、且离 agent ≤ 3 m 的点 → **Look 类候选池**，按离该侧候选的距离由近到远排序，每侧最多 12 个；
   - Look 池和直接池的提议 1:1 交替；
   - Flip 的 w1 从 B 侧的 Look 池取点，Stay 的 w1 从 A 侧的 Look 池另取一个点；
   - 投影只是**提议筛选**。是否合格仍完全按渲染出的掩码和 METRICS_SPEC 判定：v0 两个世界 X 掩码为 0、首步证据 ≥ 250、可解性、距离比、物理有效。

## 补充 7（2026-11-08 18:25，人类批准：候选放宽；与补充 6 一起进入下一轮）
**原因**：「两个候选必须同类」是产出的主要瓶颈之一。多数场景天然没有两个同类物体，只能靠复制，而复制常失败：第二轮 24 个场景里，8 个场景复制 6 次全部失败，一次尝试都没做成；还有 2 个复制成功的场景，又卡在恢复基线出错上。
1. **候选**：v0 画面中任意两个可拾取物体 A、B，可见性和距离要求不变：各自掩码 ≥ 250、离 v0 ≤ 1.5 m、都带标号。有同类的组合时优先用同类，没有就用不同类。
2. **锚点 X**：在场景中类别唯一，与 A、B 都不同类，不滚动（补充 3）。距离比、唯一性等其他条件都不变。
3. **指令**：`Select the marked object closest to the <锚点类别>.` 标号只加在 A、B 两个候选上，任何其他物体都不带标号（T02 §2 的 success_eligible 只对 A、B 成立）。
4. **默认不再复制候选。** 复制相关代码保留但不启用。补充 6 第 3 条的恢复错误仍要查清，因为 FloorPlan212 在天然候选下也出现过。

## 补充 9（2026-11-08 19:45，Claude 根据 E2E 首对的诊断补充；只改构造与渲染方式，不改任何阈值）
**发现**：E2E 首对里，锚点和候选都不在画面中，两个世界的画面差却超过 3。差异集中在两把椅子和桌边，记录显示椅子在两个世界的位置差 0.12 mm 和 0.05 mm。原因是两个世界**各自做了一次物理落定**，与锚点无关的物体也会有亚毫米级抖动，物体边缘的渲染就不同了。
- 这对直接类不构成问题（补充 8）。
- **但对 Look 类是致命的**：Look 要求起点画面在两个世界中几乎逐像素相同（最大通道差 ≤ 3）。任何一件家具的抖动都会让它不合格；到了 T02，视角表里只要有一个状态出现抖动，整对就被丢弃。这很可能是 Look 一直为 0 的主要原因之一，「既没藏住、也不够直接」（neither_hidden_shared_prefix_nor_direct_evidence）里应该有不少是这种情况。

**改法：**
1. **w1 的快照 = w0 的快照，只替换锚点 X 的位姿。**
   - w1 照常放置 X、落定，照常检查物理有效：X 偏差 ≤ 2 cm，其他物体相对基准 ≤ 1 cm。阈值不变。
   - 但保存的 w1 快照里，除 X 以外所有物体都直接沿用 w0 快照中的位姿，X 用 w1 落定后的位姿。物理检查已经保证其他物体在 w1 中的真实位移 ≤ 1 cm，所以这仍然是物理有效的世界。
2. **所有渲染都在物理暂停下进行。** 生成时的前缀检查、见证回放、T02 导出，都用 `PausePhysicsAutoSim`（或 AI2-THOR 5.0 中等价的做法），让物体在恢复快照后不再被推动。恢复后用只读元数据确认每个物体的位姿与快照一致。做不到逐位一致的，报告最大偏差。
3. 前缀规则不变：最大通道差 ≤ 3，且 X 掩码为 0。
4. **报告**：把「neither_hidden_shared_prefix_nor_direct_evidence」拆成两类计数：「X 在 v0 可见」和「X 不可见但画面差 > 3」。前者是放置问题，后者是抖动问题，以此验证上面的判断。修改前后各报一次。
5. E2E 的视角表导出也按第 1、2 条做。
