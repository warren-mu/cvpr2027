## 706439：Ray socket 路径过长

原始异常在 `ray.init → Node._prepare_socket_file`，尚未进入模型初始化：

```text
OSError: validate_socket_filename failed: AF_UNIX path length cannot exceed 107 bytes
```

Ray 将 `/ray/session_<日期微秒>_<PID>/sockets/plasma_store` 附加到原本已含完整 run 名与 PBS ID 的 `RAY_TMPDIR`，触发 Linux Unix socket 路径限制。原异常和路径保留在 [train.log 压缩原件](../logs/runs/t00b_scale8_baseline/evidence/train.log.part00000.gz)；[evidence_index.json](../logs/runs/t00b_scale8_baseline/evidence_index.json) 记录原始 SHA `07327f252505fca38df45905d7983622db0094040ee0e7ef370cdb7864caae32` 及压缩分片 SHA。

修复使用 [ray_scratch.py](../src/tools/ray_scratch.py)，为每个 run/variant 在 `CVPR_SCRATCH/r/<6hex>` 原子创建独占目录，权限 0700；碰撞另取名，保留所有旧目录。按实际 Ray 后缀预留 10 位 PID，提前检查完整 UTF-8 路径不超过 107 字节；过长的自定义 scratch 路径明确失败，不回落到 home 或其它目录。目录写入 run 的 `ray_temp.json`、配置和日志。2/4/8 卡入口共用这个运行目录修复，未改变训练参数、拓扑或计时定义。

[正式 CPU 检查结果](../results/t00b_ray_scratch_cpu_checks.json) 在提交 `b7e4a5920ec3ea97b864d4bb1553dc1fafaafafd` 上 exit 0；[日志](../logs/runs/t00b_ray_scratch_cpu_checks.log) 记录 5 项测试全部通过，覆盖旧长路径、107 字节/Unicode 边界、独占目录、碰撞与旧证据保护、scratch 越界拒绝。测试没有启动 Ray 或 GPU。

随后 706436 已采用短路径并越过 Ray 初始化，进入 vLLM 模型加载，说明本次实际路径长度故障已被绕过；这不等于训练完成。其实际路径记录见 [4 卡配置](../logs/runs/t00b_scale4_baseline/config.json) 和 [Ray 路径记录](../logs/runs/t00b_scale4_baseline/ray_temp.json)。

## 706436：Triton launcher 导入 ENOENT

4 卡在 vLLM 模型加载后、KV cache profiling 阶段失败。Ray 最外层的 `UnserializableException` 包含底层真实异常：

```text
torch._dynamo.exc.BackendCompilerFailed: backend='inductor' raised:
ImportError: .../cache/triton/cGv58Ouk6b5PSKRuM7rGvsH_D8MSZee_7392Yywxru0/__triton_launcher.so:
cannot open shared object file: No such file or directory
```

栈为 `vLLM profile_run → Torch Inductor → Triton compile_module_from_src → module_from_spec`。这是编译产物导入失败；原始记录没有 OOM 或 watchdog timeout。完整异常保留在 [train.log 压缩原件](../logs/runs/t00b_scale4_baseline/evidence/train.log.part00000.gz)；[索引](../logs/runs/t00b_scale4_baseline/evidence_index.json) 的原始 SHA 为 `8076ff9a06a07f5977912ad23723fda051dcd2af1389cdf7963af4cc24ea0b79`。

故障后只读检查时，该 `.so` 文件已存在。这个后续文件观察不证明失败时文件可见，也不能单凭它判定竞争或文件系统是根因。实装 Triton 3.2.0 的缓存代码先检查文件，缺失时构建后以 `os.replace` 写入，再加载；**ENOENT 的底层原因仍未知**。

缓解方案是 [t00b_compile_cache.py](../src/tools/t00b_compile_cache.py)：训练子进程仅覆盖 `TRITON_CACHE_DIR` 与 `TORCHINDUCTOR_CACHE_DIR`，分别指向该 run/variant 的 `work/compile_cache/triton` 和 `work/compile_cache/inductor`。新根目录独占创建、拒绝重用；旧共享缓存和新缓存全部保留。同一 run 的 ranks 仍共享该 run 的缓存，未做 per-rank 隔离。HF/下载缓存、HOME、CUDA mask、Ray 路径及官方 compile/eager 参数均不因此改变。配置、`T00B_COMPILATION_CACHE` 日志和资源原始记录保存实际路径与之前的两项值。

[正式 CPU 检查结果](../results/t00b_compile_cache_cpu_checks.json) 在提交 `1d88fcd4f405337b56c401eec70d83a678a2365f` 上 exit 0；[日志](../logs/runs/t00b_compile_cache_cpu_checks.log) 记录 4 项测试全部通过，覆盖只改变两项环境变量、run/variant 隔离、旧缓存保护和 PBS/manifest/scratch 错配拒绝。CPU 检查不验证 GPU 编译成功；此处只能称为**缓存隔离缓解，实际有效性待重试验证**。新缓存的编译启动与首步成本必须照实计入，不能从训练计时中扣除。

对固定 VAGEN/VERL 和实装 Ray 2.60 源码的只读检查未发现这两项变量被覆盖：monitor 在启动训练前传入子环境，Ray 启动进程复制继承环境，`runtime_env.env_vars` 逐键合并，VERL actor 只增加 rank/world/master 等字段。这是源码层面的继承验证，尚非重试中逐 actor 的实测环境快照。共享入口、监控和解析源码分别为 [scale wrapper](../experiments/t00b_scale_smoke.sh)、[scale monitor](../src/tools/t00b_scale_monitor.py)、[scale parser](../src/tools/parse_t00b_scale_log.py)。

对 vLLM 的核对限定于本次实际失败路径：归档 train.log 记录 V0 v0.8.2、TP=4、`enforce_eager=False`；未设置的 compilation level 使用源码默认 0。profile_run 内 TP>1 的 embedding helper 使用自身的 `torch.compile` 装饰器，CUDA 的 simple backend 为 Torch Inductor，失败路径也直接指向原 TRITON_CACHE_DIR。这个路径没有进入 vLLM 的 VllmBackend 缓存覆盖，因此本次未增改 VLLM_CACHE_ROOT。vLLM 的 PIECEWISE/V1 路径确有将两项环境变量改向其内部缓存的代码，不能把当前继承结论外推为“vLLM 永不覆盖”。此处仍是既有日志和安装源码核对，不是新的 GPU 编译成功证据。
