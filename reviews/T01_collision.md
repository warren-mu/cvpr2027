## 对三个问题的回答

### 1. 支持接触与穿透怎么区分
不再用任何「碰撞查询」来判定穿透。两个原生 API 都把「物体放在桌上」这种支持接触也算作碰撞（33/35 被拒），也给不出穿透深度，所以无法区分。

改用物理引擎自己的反应来判定：**穿透的物体，一旦恢复物理模拟就会被引擎推开。** 具体做法：
1. 用 AI2-THOR 给出的合法放置点放置物体（`GetSpawnCoordinatesAboveReceptacle` 等接收面采样），再用 `SetObjectPoses` 传完整列表写入；
2. 恢复物理，推进到 `isSceneAtRest=true`，最多 N 步，N 写进配置；
3. 落定后，被编辑物体的**位置**与指定位置偏差 ≤ 2 cm，其他所有可移动物体的**位置**变化 ≤ 1 cm，并且被编辑物体的 `parentReceptacles` 包含目标接收面。

以上就是 METRICS_SPEC §1「物理有效」的测量方式，阈值不变。METRICS_SPEC 只规定位置阈值；旋转的浮点级变化（如 3e-5°）不属于判定项，记录即可，不作为停止条件。

### 2. 覆盖哪些几何
覆盖完整位姿列表里的全部可移动、可拾取物体。墙、地板、固定家具这类静态结构，通过上面的落定反应间接覆盖：物体如果嵌进静态结构，落定时会被推开，或者掉出场景。不需要、也不允许按名字忽略 Floor 或接收面。

### 3. 测量动作的副作用
测量只用只读的元数据和渲染，**不再执行任何会改动状态的「测量动作」**（原位 Teleport、碰撞 helper）。改动状态只发生在构造步骤里。每个世界构造完、落定后，保存一次完整快照（完整位姿列表 + agent 位姿），之后的渲染和回放都从这个快照恢复。

### 附：FloorPlan205
原始场景本身没有落定（SideTable 一直在下落）。这是场景的问题，不是方法的问题。规则：每个场景生成前先做一次落定预检；原始场景推进 N 步后仍未静止，或者有物体位移超过 1 cm，就整个场景排除，记录原因。

## 关于 D/E/F/G 诊断的结论（供 D1 使用）
- **E（同一进程、agent 不动，编辑后再撤销）**：19/20 逐像素一致，唯一不一致的案例只差 1 个像素、最大差 1。这是构造世界对最接近的条件。
- **D/F（TeleportFull 回原位、离开再返回）**：`cameraHorizon` 出现浮点漂移（30.0000038 → 30.0000076），伴随局部差异，最大到 46。所以构造世界对时 **agent 不能动**。
- **G（跨进程）**：几乎每个案例都有大面积低幅差异（≤3）。所以同一个状态在不同进程里渲染，不保证逐像素相同。

由此得出 D1 的建议（需人类批准，见 STATUS.md）：**实时渲染 + 前缀共用。** 在同一个进程里、agent 不动，渲染 w0 和 w1 的前缀，满足两条才算信息一致：两帧的最大通道差 ≤ 3，且被编辑物体和锚点在前缀里不可见（掩码像素为 0）。之后在训练和评测中，两个世界共用同一组前缀帧，这样智能体收到的输入逐字节相同。METRICS_SPEC §1 已按此写明实现方式。
